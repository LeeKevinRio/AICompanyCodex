# 工作流程

1. **接案**：總監整理目標使用者、問題、平台與限制，列出假設。
2. **定義**：產品經理寫出本輪範圍、排除項目、可觀察的驗收條件。重大的方向問題交創辦人決定。
3. **規劃**：設計師與技術主管提供必要的畫面、流程、架構及工作拆分。
4. **開發**：工程師逐項實作，同步維護待辦與重要決策。
5. **內部驗證**：依風險檢查主流程、錯誤情境與回歸範圍；保存實際結果。
6. **交付**：總監提供可操作成果、查看方式、測試結果與已知問題，狀態設為「待創辦人驗收」。
7. **回饋**：創辦人要求調整則回到需求與開發；明確通過後才記錄為「已驗收」。
8. **發布**：另行確認發布目標與授權，檢查部署條件與回復方式後執行。

## 狀態

待釐清 → 已規劃 → 開發中 → 內部驗證 → 待創辦人驗收 → 已驗收。

另記錄「受阻原因」與「發布狀態」，不要用「已發布」取代驗收紀錄。需要修改的項目回到已規劃或開發中，保留原回饋。

## 收尾與交接

每輪更新 `project/status.md`，重要決策更新 `project/decisions.md`，需求變動更新 `project/backlog.md`。交付使用 `templates/acceptance.md`，需要角色交接時使用 `templates/handoff.md`。只有實際執行過的測試可填通過；未執行須寫原因。

- 每次提問、需求修正及交付，總監整理現有八位成員的本輪進度，不能只報有做事的角色。這是按職責分列的回報，不更改職称或假稱八人各自執行。
- 固定列出：林知衡（總監）、許映辰（產品）、沈若晴（設計）、周以承（技術）、陳予安（前端）、程修遠（後端）、葉見微（測試）、何穩舟（維運）。
- 各列寫「已完成／進行中／受阻／無」及一句具體成果或阻礙；沒有本輪工作一律填「無」，不得用舊成果充數。受阻不填無。
- 長任務開始時說明負責事項，取得實質進度或遇到阻礙時更新相關列；每輪最終回覆附完整八列。不要為了回報而中斷已授權工作等待確認。
- 單一代理可依序承擔多個職責，明確以職責整理；只有真正使用多個代理時才可說各代理獨立執行。自我檢查仍是自我檢查。
- 先直接回答問題與主要結果，再附進度表；沒有實作的純問答也要列出實際查證職責，其餘填無。
- 新增費用、登入驗證、必要產品決策等真正需要創辦人介入的事項才提出；例行開發、測試、依既有授權提交與推送直接完成。
